# Release process

ResolveOps releases are intentionally conservative. A release candidate should be reproducible, reviewable, and tied to an exact Git commit.

## Pre-release checklist

Before publishing a release:

1. the target commit is on `main` and the working tree is clean;
2. GitHub CI is green on every supported Python version;
3. Ruff format and lint, strict MyPy, pytest, branch coverage, architecture checks, secret/static-security checks, and `pip-audit` pass;
4. generated schemas match the canonical models;
5. `python scripts/check_release.py --tag v<version>` passes for the intended tag;
6. source and wheel distributions build successfully;
7. Twine metadata validation and wheel-install smoke testing pass;
8. release artifacts are built from the exact tagged commit;
9. the changelog, citation metadata, security model, limitations, and release-validation record are current;
10. no real customer data, credentials, transient build output, or validation scratch files are present.

## Release artifacts

For a public release, retain or attach as appropriate:

- source distribution;
- wheel;
- SHA-256 checksums;
- SBOM when generated by the release workflow;
- release-validation summary;
- relevant release notes.

## Tagging and publication

The expected tag format is `v<project version>`, for example `v0.1.0rc2`.

PyPI publication remains an explicit maintainer action for the `0.1` line. Do not publish from an unreviewed branch or from artifacts that were built before the release commit was finalized.

## Production claims

A successful package release does not imply that ResolveOps is approved for production deployment. Production deployment criteria are broader than packaging and CI and are documented in [`security-model.md`](security-model.md) and [`limitations.md`](limitations.md).
